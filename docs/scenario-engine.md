# Scenario engine

Scenarios are the declarative half of a loader definition. The engine
(`src/rsa/scenario.nim`) knows seven step kinds and nothing about specific
loaders.

## Execution model

`runScenario(loader, vars)` iterates `loader.scenario` in order and calls
`runStep` for each item. Steps run with the target directory as the current
directory (`flow.install` changes into it first). Any raised `RsaError` aborts the
scenario and the installation.

Every string field is expanded before use with the current variable set:

| Variable | Source |
| --- | --- |
| `{mc}` | selected Minecraft version |
| `{loader}` | selected loader version |
| `{installer}` | selected installer version, or the loader version when the loader has no separate installer source |
| `{dir}` | absolute target directory |
| `{file}` | file written by the last `download` step (empty before the first one) |
| `{loaderId}` | loader id |
| `{loaderName}` | loader name |

Expansion is a simple textual replacement of `{key}` tokens via
`util.expand`. Unknown placeholders are left untouched. There is no escaping
mechanism; a literal brace sequence that looks like a known placeholder will be
replaced.

## Steps

### `download`

```json
{ "type": "download", "url": "https://…/{loader}.jar", "file": "server.jar" }
```

- `url` is required; an empty URL is an error.
- `file` is optional. When empty, the last path segment of the URL is used
  (`util.fileBaseName`), falling back to `download` for URLs ending in `/`.
- Parent directories of `file` are created.
- The response body is buffered and then written. A failure removes the partial
  file and raises.
- On success `vars.file` is set to the written path.

This is the only step that changes `{file}`.

### `run`

```json
{ "type": "run", "command": "java -jar \"{file}\" --installServer", "optional": false }
```

- Executes `command` with `execCmdEx`, i.e. through the system shell.
- Stdout/stderr are captured. On a non-zero exit code the last 12 lines are
  included in the error message.
- `optional: true` turns a failure into a hint and continues.
- The engine does not stream output; long installers appear silent until they
  finish.

### `write`

```json
{ "type": "write", "file": "user_jvm_args.txt", "content": "-Xms2G\n-Xmx6G\n",
  "overwrite": false }
```

- `file` is required; parent directories are created.
- `overwrite` defaults to `true`. With `false`, an existing file produces a hint
  and the step is skipped.
- `content` is written verbatim after template expansion. JSON string escapes are
  the usual `\n` etc.

### `replace`

```json
{ "type": "replace", "file": "run.sh", "find": "old", "replace": "new",
  "onlyIfExists": true }
```

- Replaces **every** occurrence of `find` (Nim `strutils.replace` semantics).
- If the file is missing: ignored when `onlyIfExists` is `true` (default), an
  error otherwise.
- An empty `find` is an error.

### `mkdir`

```json
{ "type": "mkdir", "file": "mods" }
```

Creates a directory, including missing parents. The path is carried in the `file`
field for consistency with the other steps.

### `require`

```json
{ "type": "require", "file": "run.sh", "optional": false }
```

Verifies that a file (not a directory) exists. This is the post-condition check
for installer-based loaders: if the installer silently failed to produce
`run.sh`, installation stops here. `optional: true` downgrades a missing file to
a hint.

### `copy`

```json
{ "type": "copy", "source": "config/defaults/server.properties",
  "target": "server.properties", "optional": false }
```

Copies one file. Parent directories of `target` are created. A missing source is
an error unless `optional` is `true`.

## Installer-based loaders

NeoForge and Forge follow the same pattern:

```json
"scenario": [
  { "type": "download", "url": "…installer.jar", "file": "installer.jar" },
  { "type": "run", "command": "java -jar \"{file}\" --installServer" },
  { "type": "write", "file": "user_jvm_args.txt", "overwrite": false,
    "content": "-Xms2G\n-Xmx6G\n" },
  { "type": "require", "file": "run.sh" }
],
"launch": "./run.sh nogui"
```

Fabric instead downloads the launcher jar and lets it fetch the vanilla server on
first start:

```json
"scenario": [
  { "type": "download",
    "url": "https://meta.fabricmc.net/v2/versions/loader/{mc}/{loader}/{installer}/server/jar",
    "file": "fabric-server-mc-{mc}-loader-{loader}-launcher-{installer}.jar" }
],
"launch": "java -jar \"{file}\" nogui"
```

Because Fabric's launcher needs the server jar name at launch time, `{file}` in
`launch` resolves to the last downloaded file.

## Start script

After the scenario, `flow.install` expands `launch` and calls
`preconfig.writeStartScript`:

```sh
#!/usr/bin/env sh
# Generated by RedstoneServerAssembler
cd "$(dirname "$0")"
exec <launch>
```

The script is made executable (`0755`). The marker protects user files: if
`start.sh` exists and does not contain the marker, it is left untouched and a
hint is printed. An empty `launch` disables the step entirely.

## Security

A loader definition can run arbitrary shell commands through `run`. Treat loader
JSON files like executable code and only install definitions from sources you
trust.
